# Grok Bot AI 自媒体情报、选题、文案与知识迭代系统

**产品需求文档（PRD）＋技术实施指南｜V1.0 草案**  
编制日期：2026-10-30  
交付对象：Grok Bot / Pi Agent（先阅读、复述、核验，再分阶段实施）  
状态：**需求设计文件，未部署、未授权外部执行、未验证接口能力**

> **一句话目标**：以用户的 X 关注账号为首要情报源，以 X 平台相关讨论和用户指定的 AI 热点站为主要补充，结合少量海外真实 AI 应用案例，自动整理候选信息、分析目标用户、推荐 5—10 个选题；用户选定约 3 个后，按平台每题生成**一份**初稿，反复按用户意见修订；发布后复盘，并把事实、偏好、假设和经验证的经验分别沉淀到 **Notion**。系统部署在 Grok Bot 可用的执行环境，但代码和重要状态必须可独立恢复。

---

## 0. 先给执行者的要求

1. **先做能力审计，不得把“已连接账号/插件”视为“已具备可编程读写权限”。** 先核验 Grok Bot/Pi Agent 是否能读取 X 关注列表与帖子、读取 Notion 并新建/更新页面、访问 aihot.news、读取指定 GitHub/飞书数据、持久化任务、定时执行、在云环境清空后恢复。
2. **先做小规模端到端样例，再做自动化。** 不得在接口未核实前承诺全自动；无法自动获取时提供人工提交链接、文本或文件的降级方案。
3. **未经用户批准，不得购买服务、充值、部署收费资源、发布社交媒体内容、扩大数据权限、合并到生产分支或删除既有资料。** 允许先在独立实验分支创建草稿 PR；任何真实账号授权均需用户参与确认。
4. **不开发国内平台抓取器。** 只预留 GitHub、飞书两个“国内信息输入口”，由用户独立建设国内采集流程。本项目只读指定数据，不负责采集抖音、小红书。
5. **Notion 是唯一正式业务知识库**；GitHub 是代码、配置、规则模板、数据导出备份及恢复脚本的版本库；飞书/GitHub 国内入口是外部输入，不得被误写成另一套主知识库。
6. **任何判断必须可追溯来源。** 不伪造阅读、实测、营收或平台数据；不以热门、点赞或用户偏好直接证明传播规律。
7. 每个阶段提交：实际执行记录、成功/失败证据、费用、权限变化、待确认事项、恢复方法；没有完成的明确标记“未完成”。

## 1. 产品范围与边界

### 1.1 目标用户与定位（初始假设，待内容反馈验证）

面向中文普通用户：①想把 AI 用于工作提效的职员、小老板；②不会编程但想借 AI 做工具、应用或自动化的人；③关注个人 AI 项目、副业与真实创业案例的人。优先解释“对谁有什么用、如何开始、有哪些限制”，不追逐所有技术新闻。

### 1.2 V1.0 必须具备

- X 已关注账号优先的资讯收集；X 平台相关话题/搜索为次级来源；用户提供的 **https://aihot.news/** 为另一核心来源；海外普通人 AI 提效/收入/就业/创业案例作为低优先级补充。
- 国内数据的两个只读接入口：指定 GitHub 路径和指定飞书位置，未配置时不影响主流程。
- 原始信息去重、分类、来源记录、可信度初判、用户需求证据提取、知识库检索。
- 每轮从候选素材（例如 100 条，非硬性抓取指标）形成 **5—10 个选题建议**；用户人工决定做哪些（例如 3 个）。
- 对用户选中的**每个选题、每个指定平台，先只生成 1 份文案**；用户不满意则按反馈修改同一稿件并保存版本。绝不默认每题同时输出三种方案。
- 用户自行制作与发布视频；录入或导入表现数据；复盘并将验证状态明确的记录写入 Notion。
- GitHub 版本管理、可重复部署、备份导出、故障恢复演练。

### 1.3 V1.0 不做

国内平台自动爬虫；自动视频生成/剪辑；自动发布；买量；复杂多 Agent 架构；自建大型数据仓库；承诺“自动打造爆款”；未经授权的 X 数据批量获取；无限制收集第三方内容。

## 2. 总体架构：一个主工作流＋几个可替换连接器

```text
[X 关注账号/关注列表] --首要--> [X 读取适配器] -----┐
[X 话题/搜索] ---------次要--> [X 读取适配器] -----┤
[aihot.news] -----------核心--> [站点读取适配器] ---┤
[海外 AI 应用案例] -----补充--> [案例检索适配器] ---┤
[GitHub 国内数据目录] --预留--> [只读适配器] -----┤
[飞书国内数据位置] ----预留--> [只读适配器] -----┘
                                                   ↓
                              [统一素材池：标准化/去重/来源/时间]
                                                   ↓
                              [用户需求证据 + Notion 知识检索]
                                                   ↓
                              [选题排序：5—10 个 + 理由 + 反证]
                                                   ↓
                                  【用户选定约 3 个题目】
                                                   ↓
                               [按平台每题 1 份文案初稿]
                                                   ↓
                          【用户修改意见 → 迭代同一文案版本】
                                                   ↓
                                    【用户自行制作、发布】
                                                   ↓
                              [发布数据/评论/对照案例 → 复盘]
                                                   ↓
                   [Notion：事实/素材/偏好/假设/验证经验/历史版本]
                                                   ↺

GitHub 私有仓库：源代码 + 提示词/规则版本 + 依赖锁定 + 备份导出 + 恢复脚本
Grok Bot/Pi Agent：运行与交互（视实际能力），不作为唯一持久化存储
```

**实施原则**：先以一个可复现的 Python 或 Node.js 小项目实现连接器、调度、存储适配和提示词模板；Pi Agent 负责开发和运行编排。不是必须安装 TopicEye/Easel 全套软件。可参考 TopicEye 的多源去重和选题评估思路、Easel 的策划—创作—反馈流程，但以实际代码、许可证、部署条件为准，避免引入重型依赖。

## 3. 信息源策略与优先级

### 3.1 A 级：用户 X 关注账号（最优先）

**输入**：用户授权的 X 账号；已关注的约 100 多个账号；用户未来新增的重点账号列表。**账号名称、凭据和关注列表目前未在本文件提供，必须在实施时读取授权账号或由用户补充**。

**目标**：收集近期帖子及其中链接、教程、工具实测、工作流、开源项目、实操案例；优先考虑作者一手经验、可复现方法与普通人的实际价值。

**具体机制**：
1. 检查 Grok Bot 已有 X 连接能否实际列出关注账号、读取时间线/用户帖子、按日期增量获取；记录可用操作与额度。
2. 如不可用，评估 X 官方 API 的具体权限、费用、速率及许可；由用户确认是否使用。禁止擅自绕过登录验证、访问控制或平台规则。
3. 仍不可用时，以用户维护的账号名单＋手动转发帖子链接/导出允许的数据为 MVP 入口；**不可将“已连接 X”当作已打通自动采集**。
4. 每次仅取上次检查时间之后的新增记录；去重使用平台帖子 ID/规范化 URL；保存作者、发布时间、采集时间、原文摘要、链接、媒体类型、可用互动指标、相关工具和使用场景。
5. 对外部帖子的内容以**概述、引用链接、再验证和原创中文解读**为主；避免未经授权直接复制完整文字、视频或图片。

### 3.2 B 级：X 相关话题与平台发现

围绕 AI 自动化、AI 编程、普通人 AI 工具、AI 工作效率、个人创业等主题，通过合法可用的搜索/趋势入口寻找高信号帖子。防止 X 热门娱乐内容挤占配额。优先抓**真实演示、工具链接、操作步骤、失败经验**，而非只有营销标题的内容。

### 3.3 B 级：用户指定站点 aihot.news

**指定地址：** https://aihot.news/ 。用户表示该站聚合大量 AI 信息源；此为用户提供的背景，**尚未确认其是否有公开 API、RSS、登录要求、robots 规则或稳定可解析结构**。

实施顺序：查看站点公开 RSS/API/导出能力 → 核实网页可访问与使用条款 → 如允许，再建立低频、增量、带缓存的读取方式 → 不可用时接受用户提供链接或文件。避免与 X 内容重复；该站重点补足重要新产品、发布、工具更新，不应覆盖用户关注账号的优先级。

### 3.4 C 级：海外普通人 AI 应用案例（补充，不喧宾夺主）

候选渠道：Indie Hackers、Hacker News 的 Show HN/经验帖、Reddit 公开讨论、Product Hunt 产品评论、公开创业者访谈与个人博客。渠道是否可自动读取、API 条款、商业许可及访问限制，需逐个核实；不要求一次接完。

寻找的案例类型：个人用 AI 获得实际收入；普通员工减少重复劳动；小企业主用 AI 节省工时；不会编程者做出可用产品；求职者用 AI 改善求职流程。**不得把“使用 AI 后找到工作”直接解释为 AI 造成的结果**；记录时间、行动、其他因素及证据。

真实性分级（本系统建议的暂行字段，并非用户既有指南原文等级）：`官方/可复核材料`、`当事人自述`、`第三方转述`、`未核实`；收入数字须注明货币、期间、毛收入/利润及证据是否存在。禁止以无凭据的“月入 X 万”当成确定事实。

### 3.5 D 级：国内数据入口（只读，暂不开发采集）

- **GitHub 入口**：配置仓库、分支、目录和访问凭据（私有仓库优先最小只读权限）。读取 JSON/CSV/Markdown，按唯一 ID 或内容哈希增量导入。
- **飞书入口**：配置多维表格或云文档位置、应用权限、分页读取方式；需实际验证个人账号权限与连接方式。
- 两者可能包含相同素材，按 `source_platform + original_url/post_id` 跨入口去重；不把两次同步当成两条独立证据。
- 接口暂时不可用时，用户可上传 CSV/JSON 作为降级输入。

### 3.6 配额与排序原则

**不是“抓满 100 条才运行”。** 每轮优先保证有价值的新信息。建议初始来源权重：X 关注列表最高；X 发现与 aihot.news 次之；海外案例补充；国内数据可选。权重是可调整的运营参数，不是未经验证的最佳比例。记录各来源入库量、可用率、重复率、转化为候选选题的比例，后续根据真实效果调整。

## 4. 统一素材格式与证据约束

每条素材最少记录：

```json
{
  "item_id": "source:original_id_or_hash",
  "source_type": "x_following|x_discovery|aihot|overseas_case|github_domestic|feishu_domestic|manual",
  "source_url": "https://...",
  "author_or_publisher": "...",
  "published_at": "ISO-8601 or null",
  "collected_at": "ISO-8601",
  "title_or_summary": "...",
  "raw_reference": "link or authorized short excerpt",
  "claims": ["..."],
  "evidence_status": "verified|self_reported|third_party|unverified",
  "target_user_hypotheses": ["..."],
  "user_problem_evidence": ["comment/question/source link"],
  "tool_or_method": ["..."],
  "duplicate_of": null,
  "processing_status": "new|screened|candidate|archived"
}
```

规则：保存来源链接、时间与原始主张；不把 AI 摘要冒充原文；同一消息的多个转载不算多条独立证据；评论是样本，不自动代表总体用户；个人隐私数据最小化、必要时去标识化；对第三方内容按授权、合理引用和平台条款处理。

## 5. 核心：用户需求分析与立题引擎

### 5.1 从信息到用户问题

对每条素材输出：**信息事实是什么 → 谁可能关心 → 他们原本有什么问题 → 新工具/方法能解决哪一部分 → 有哪些直接需求证据 → 哪些是假设 → 需要核实什么**。

没有用户需求证据时，不得编造“很多人都在问”；可标为“潜在需求待验证”。同一工具可对应不同用户，不要仅按技术名称决定选题。

### 5.2 知识库调用顺序

先查 Notion 中：账号定位、已覆盖选题、目标用户问题、历史案例、用户已确认的写作偏好、已验证的运营规则；再进行候选排序。若 Notion 读取失败，标注“本轮未完成知识库检索”，可以出**临时草案**但不得声称“结合历史经验”。

### 5.3 候选选题判断维度（建议，不伪装成已验证模型）

- **真实用户价值**：解决具体问题的程度；有无用户需求证据。
- **信息可信度**：工具/案例是否可核实；是否存在夸大、过时。
- **受众匹配**：是否适合普通人、非程序员、小老板等目标群体。
- **新颖与时效**：相对已有内容是否有新信息；是否过时。
- **可讲清与可验证**：能否用具体例子、演示或清晰步骤说明。
- **传播潜力假设**：标题张力、冲突、收益与风险，但不得用夸张取代事实。
- **制作成本**：是否需要复杂实测、授权素材或昂贵工具。

可先使用人工可解释的分级（高/中/低）而非伪精确总分；若后续要加权评分，必须记录权重版本和验证结果。对每个候选都提供**最强反证或可能不值得做的原因**。

### 5.4 推荐给用户的 5—10 个选题卡

每张卡固定包含：

1. `选题编号`、`拟定标题`、`建议平台`；
2. `面向谁`、`他们想解决什么问题`；
3. `核心价值一句话`、`为什么现在值得讲`；
4. `原始信息来源`（至少一条可打开链接）、`需求证据/缺口`；
5. `可信度与风险`、`最强反证`；
6. `与已做内容的差异`、`制作难度`；
7. `推荐级别与理由`（可解释，不承诺爆款）。

**第一次人工关口**：用户明确选择 1—3 个或更多选题；未选中的保留候选状态，不能自动生成/发布成品。用户可直接提出自己的题目，系统仍须补证据与边界。

## 6. 文案引擎：每题每平台只写一份，持续修改

### 6.1 触发规则

用户选定选题并指定平台（抖音、小红书或两者）后，系统为**每个“选题×平台”组合只生成一份初稿 V1**。例如选择 3 个选题、只做抖音，就输出 3 份；如每题都指定抖音＋小红书，则输出 6 份。**不得默认给每题 3 个版本供选择。**

### 6.2 文案生成前的检索

读取 Notion：用户已确认偏好、该平台写作规范、相关案例及反例、选题事实来源、禁用表达、上次修改记录。对时效性强的工具功能重新核验。文案中的收益、时间、效果和价格不得编造。

### 6.3 平台差异（作为初始写作假设，后续用数据校正）

- **抖音**：口语化、开头迅速点出问题或反差；主体用具体操作或案例解释；节奏清晰，适合口播；不为刺激而夸大。
- **小红书**：强调适用人群、使用场景、步骤和可保存的清单；标题明确收益/问题，正文易扫描；保持真实、可操作。
- 时长、字数、结构不得写死为“平台算法规则”；由用户账号定位、实测表现及当前平台规范决定。

每份交付：标题、正文/口播稿、必要镜头或画面提示（可选）、事实核对清单、来源链接、未证实内容提醒；不要自动生成视频。

### 6.4 用户修改循环与“记住我的喜好”

```text
初稿 V1 → 用户指出不满意之处 → 系统复述修改要求
       → 修订稿 V2 → 用户再反馈 → V3 … → 用户确认最终稿
```

**不能依赖 Grok Bot 对话记忆长期可靠。** 用户反馈应明确写入 Notion，至少分为：

- `本稿局部修改`：只改当前文章，不推断为长期偏好；
- `用户明确确认的长期写作偏好`：如“以后开头少用空话”，标明确认日期、适用平台与例外；
- `待验证运营假设`：如“问题式开头更容易完播”，必须等真实数据支持，不可因为用户喜欢就升级为平台规律。

每次修订保存 `draft_id / version / feedback_text / interpreted_change / change_summary / accepted_by_user / timestamp`；未经用户确认的总结不得写成“用户永久偏好”。当新反馈与旧偏好冲突，先展示冲突并请用户选择适用范围。

### 6.5 参考爆款与非爆款

可以建立“**内容案例与效果库**”，既收集表现好的，也收集普通和较差的内容，避免只看成功者。尽量记录平台、账号规模、发布时间、主题、开头、结构、互动指标、评论问题、可能的外部因素。**播放量高不证明文案因果有效**；案例只作为写作候选机制，未经对照不升级为规律。不得未经许可批量下载或复制第三方视频全文。

**第二次人工关口**：用户确认最终稿；系统不自动发布。

## 7. Notion 知识库：长期资产与可验证迭代

### 7.1 依据与定位

本节采用用户此前提供的《通用知识库建设与维护指南 V1.0》的核心原则：**导航、原始资料、经验知识、维护规则、检索决策、质量验收**；以“建库—收新料—查库做决定—反馈更新”为循环。该指南中未显示的表格/等级细目，本文件不冒称已完整读取；以下字段设计属于本项目的实施建议。

**Notion 为正式知识库**。建议首页 `AI自媒体外脑 / Home`，下设关联数据库，而非把所有内容堆进一篇长文：

| Notion 数据库 | 用途 | 关键字段 |
|---|---|---|
| 01_原始素材 | X/AI号/案例/国内输入的来源记录 | item_id、URL、作者、日期、来源、状态、证据等级 |
| 02_用户需求 | 真实评论、问题与用户场景 | problem_id、用户类型、问题、证据链接、频次/样本局限 |
| 03_选题决策 | 候选、推荐理由、用户选择与否决 | topic_id、关联素材/需求、判断、版本、选择结果 |
| 04_文案与版本 | 各平台文案、反馈、最终确认 | draft_id、topic_id、平台、版本、修改原因、状态 |
| 05_内容案例 | 外部案例与自身内容的对照记录 | case_id、平台、主题、可得指标、局限 |
| 06_发布与复盘 | 用户实际发布表现、假设与检验 | publish_id、topic_id、数据时点、结果、原因假设 |
| 07_规则与经验 | 账号定位、平台写作规则、用户偏好、验证经验 | rule_id、适用范围、证据、状态、版本、责任人 |
| 08_维护与审计 | 同步、冲突、失败、修订和回滚 | event_id、对象、前后版本、操作、结果、时间 |

为降低 MVP 复杂度，第一轮可合并为 5 个库（素材、需求、选题、文案、经验/复盘），但逻辑字段必须保留，后续再拆分。

### 7.2 知识生命周期与防污染

记录状态：`待验证 → 已验证 → 正在使用 → 需要复核 → 已过时`；保留历史版本，不直接覆盖旧预测。另独立记录**知识性质**：`原始事实`、`当事人自述`、`用户偏好`、`AI 推断/假设`、`已验证经验`。**状态和性质不能混用**：例如用户确认“我喜欢简洁开头”是已确认偏好，但不等于“简洁开头更容易爆款”已被证实。

经验卡模板：`适用场景 → 原问题 → 当时判断/预测 → 依据 → 采取行动 → 实际结果 → 偏差解释（假设错误/执行差异/环境变化/运气/未知）→ 可迁移条件 → 下次复核信号`。单次数据不足时标记“待验证”。

### 7.3 读写规则

- **写入前**：查重、检查已有规则是否冲突、保留原始证据和旧版本；敏感数据最小化。
- **读出时**：按用户/平台/选题/时间过滤；优先已确认偏好与经验证经验，仍保留反例；引用知识记录 ID。
- **更新时**：AI 可自动写素材、操作日志和“待验证假设”；**提升为“已验证经验”须有预设证据标准，重要规则须用户确认**。
- **冲突时**：展示新旧结论、各自证据、适用范围；不得静默覆盖。
- **失效时**：标注已过时，不删除历史记录；保留规则变更日志。
- **定期质量检查**：随机抽查来源可追溯性、重复记录、过时产品、无证据规则、Notion 关联断链与检索命中率。

### 7.4 真实连接验收

Grok Bot 已连接 Notion 是用户提供的现状，**但 Pi Agent 仍必须亲自验证**：①列出目标数据库；②新建测试记录；③按 ID 读回；④更新指定字段；⑤查询关联记录；⑥断开/重启后重新读取；⑦清理测试数据需用户授权。若插件仅支持聊天层操作而不开放给 Pi Agent，须设计合规替代接口，不得假装已打通。

## 8. 发布反馈与 OODA 复盘

用户自行制作、发布。可手动输入：平台、视频链接、发布时间、粉丝量（可选）、曝光/播放、完播或观看时长（可得时）、点赞、评论、收藏、转发、关注增长、数据统计时点、制作形式、时长及成本。**不同平台指标口径不直接混算**。

复盘顺序：
1. **观察**：数据、评论、与自己历史同平台/相近题材的对比；样本不足则明示。
2. **定向**：分辨选题需求、标题/开头、正文、呈现形式、账号分发、发布时间等竞争解释；不要凭一条低播放视频断言文案失败。
3. **决策**：提出下一轮一个可执行调整（例如只改变开头表达，不同时改十个因素）。
4. **行动与再观察**：用户决定是否执行，记录预测与结果。

核心评估不是“这条爆了吗”，而是：**推荐的选题是否真正值得制作、内容是否帮助用户、后续判断是否因证据改善**。禁止宣称 AI 自动训练了模型权重；这里的“越来越好”指可检索规则、偏好和经验持续更新。

## 9. 技术实现建议

### 9.1 最小组件

1. **连接器层**：`x_source`、`aihot_source`、`case_source`、`github_domestic`、`feishu_domestic`；统一输出素材 JSON；每个可单独关闭。
2. **标准化层**：增量读取、URL 规范化、去重、时间/语言处理、来源与证据标记。
3. **Notion 适配层**：查询、创建、更新、关联、批量导出；错误重试要限流和幂等。
4. **业务工作流层**：`collect → screen → recommend → await_topic_approval → draft_one_per_platform → revise → await_final_approval → review`。
5. **交互层**：在 Grok Bot 聊天中用清晰编号选择选题、确认平台、逐稿反馈；不强制开发网页。
6. **任务与状态层**：存储任务 ID、上次成功同步时间、审批状态、已处理条目 ID、稿件版本；避免清空后重复抓取和覆盖。

**技术选型**：优先 Python（或 Pi Agent 当前最稳定的语言）＋少量脚本＋配置文件＋可复现依赖。可选 GitHub Actions 负责独立、无状态的定时采集，但它不能在没有 Grok Bot 外部 API 的情况下自动恢复机器人本身。无需一开始上 Docker、PostgreSQL 或多 Agent，除非能力审计证明必需。

### 9.3 幂等、故障与成本控制

- 每个输入记录有稳定 `item_id`；写 Notion 前先查唯一键；重跑不得重复入库。
- 任务状态：`pending/running/waiting_user/completed/failed`；审批点永久停在 `waiting_user`，不能因重启越过。
- API 限流、超时、失败重试次数、费用上限可配置；遇到权限/登录失败立即停止该连接器，不循环尝试。
- AI 模型与费用来源由 Pi Agent 核实；默认先小批量（如 10—20 条）测试，之后再扩到 100 条候选；记录 token/请求量和实际费用，避免臆测成本。
- 源站或 Notion 故障时，其他连接器可继续；本轮报告列明缺失信息源，不隐瞒样本偏差。

## 10. Grok Bot 云端清空后的恢复设计（硬性验收项）

**现实边界**：若云电脑被清空，正在运行的程序必然中断；本设计保证的是“资产不丢、可重建、状态可续”，**不是不经任何触发就保证继续运行**。自动恢复需要另有不随云电脑消失的外部触发器及可调用的启动接口，必须实测。

### 10.1 三类持久资产

- **GitHub 私有仓库**：代码、提示词、配置模板、依赖版本、测试、恢复文档和必要的脱敏数据导出；使用分支/标签管理稳定版本。
- **Notion**：正式业务知识与稿件/决策/反馈记录；不得只保留在聊天上下文或云电脑本地。
- **独立备份**：定期将 Notion 可导出的重要记录备份为 JSON/Markdown/CSV 到用户控制的安全位置（可为 GitHub 私有仓库中的非敏感数据目录，敏感内容需加密或放其他受控存储）。**GitHub 不自动等于 Notion 的完整备份**；必须验证导出覆盖率与恢复能力。

### 10.2 恢复流程

1. 重新获得 Grok Bot/Pi Agent 执行环境，或迁移到可用的替代执行器。
2. 拉取 GitHub 已标记的稳定版本；验证版本/依赖与校验和。
3. 从安全存储重新注入环境变量，重新授权 X/Notion/飞书（如有）；禁止把密钥写入仓库。
4. 运行健康检查：网络、权限、Notion 读写、信息源读取、状态一致性。
5. 从 Notion/备份读取上次成功游标、审批状态与文案版本；不得重复发布、覆盖已确认稿件或跳过人工审批。
6. 在测试数据上重跑一轮，再恢复正常任务。

### 10.3 必做灾难恢复演练

在独立干净环境中，从**零本地文件**恢复代码、连接、10 条样本素材、选题、一个修订稿及历史审批状态；证明数据未丢、重复导入不发生、人工审批仍生效。若 Grok Bot 无法自行定时重建，必须在验收报告中写明“需用户手动启动”或“依赖外部运行器”，不能称为无人值守。

## 11. 分阶段开发、交付物与验收

### P0｜能力审计与技术选型（先做，不收费优先）

核实：X 读取权限、X 关注列表与增量帖子、aihot.news 读取方式、Notion CRUD、GitHub/飞书只读入口、云端持久性、定时任务、外部恢复接口、预计成本。**交付**：能力矩阵（已验证/需授权/不可用/未知）、证据截图或日志、最小架构、替代方案。**未通过不得宣称自动采集已可用。**

### P1｜信息收集与标准化

先接 X 关注列表，之后 X 发现与 aihot.news，再少量海外案例；国内两个入口只建配置和读取测试桩。以 10—20 条样本证明：来源完整、增量去重、断点续传、来源失效可报告。**交付**：可运行连接器、统一 JSON、单元测试、采集报告。

### P2｜Notion 知识库与双向检索

建立 MVP 数据库及关联、模板、读写规则、去重与审计日志；验证创建/更新/查询/断开后恢复。**交付**：数据库结构、样例记录、迁移/导出脚本、恢复说明。

### P3｜用户需求分析与选题

在 20—100 条已入库信息上形成 5—10 张带证据的选题卡，用户选择约 3 个；每张卡可回溯原文与需求证据，能标记“需求未证实”。**交付**：筛选提示词、排序理由、反证字段、人工审批状态。

### P4｜单稿生成与逐轮修改

每个选题×平台仅 1 份初稿；用户反馈后只修订对应稿件，保存 V1/V2/…；区分局部意见、已确认长期偏好与传播假设；确认后锁定最终稿。**交付**：平台提示词、版本链、偏好检索与冲突处理演示。

### P5｜发布复盘与知识迭代

人工录入至少 3 条示例发布记录（可先用**标记为模拟**的数据测试）；生成带反证的复盘，不把猜测升级为事实；下轮选题能引用历史记录。**交付**：复盘模板、规则变更日志、质量检查。

### P6｜GitHub 备份、恢复和稳定版

私有仓库保存代码、规则与恢复脚本；执行干净环境恢复、重跑幂等测试、权限/密钥泄露检查；打稳定标签，记录恢复耗时与限制。**交付**：稳定标签、恢复演练证据、运行手册、已知问题与后续计划。

**统一验收底线**：每阶段有真实测试证据；没有自动发布；没有未经授权购买或登录；没有密钥入库；Notion 中每条重要结论有来源、状态与版本；用户可随时停用单个连接器而不影响其他流程。

## 12. 给 Grok Bot / Pi Agent 的首轮执行指令（请先讨论，不直接大规模实施）

> 请完整阅读本 PRD。**第一轮只做只读能力调查与方案复述**，不得安装重型依赖、修改现有项目、收费调用、采集大量帖子或创建正式 Notion 数据库。先输出：
>
> 1. 你理解的业务闭环（特别说明：X 关注列表优先；国内采集不开发；每题每平台只出一稿；Notion 是唯一正式知识库）。
> 2. Grok Bot/Pi Agent 当前真实可用的工具和权限清单，逐项给出验证方式，明确哪些尚未实测。
> 3. X 关注账号/帖子、aihot.news、Notion CRUD、GitHub/飞书入口的可行性与阻塞点；若需用户授权，列出最少必要动作。
> 4. 云端清空时如何从 GitHub＋Notion 恢复；哪些部分可自动、哪些需要人工触发。
> 5. 最简技术架构、阶段计划、预估费用及风险；优先选择可迁移、低依赖、可审计方案。

## 13. 开发时需用户补充/确认的最少信息

1. **X 账号授权方式**：由用户在 Grok Bot/X 官方流程中授权，或提供关注账号清单；**不要在聊天或文档中发送密码、Cookie、Token**。
2. **Notion 目标工作区/页面**：指定创建数据库的位置；授权 Pi Agent 可读写的最小范围。
3. **aihot.news 具体栏目或内容偏好**：默认站点首页及可公开读取栏目；如有会员功能，先确认访问方式和许可。
4. **GitHub 私有仓库**：新建独立仓库名与授权；国内输入目录、飞书位置可晚些再配置。
5. **默认文案平台**：可暂定抖音，用户选题时再指定是否需要小红书稿。

## 14. 风险、替代方案与停止条件

| 风险 | 触发信号 | 处理方式 |
|---|---|---|
| X 关注列表无法授权读取 | 连接器无权限、费用超出预算 | 先用用户维护的重点账号名单和链接提交；不绕过限制 |
| aihot.news 无开放读取方式 | 403、登录/版权限制 | 仅处理用户提供的链接/摘要，或停用该源 |
| Grok Bot 云环境不持久 | 重启丢失文件/定时器 | GitHub＋Notion 恢复；必要时独立外部运行器 |
| Notion 插件只在聊天层可用 | Pi Agent 无法 CRUD | 改用获授权 API/连接器；未打通前不得假装入库 |
| 大量低质量资讯 | 重复率高、选题证据不足 | 降低抓取量，提高关注列表优先级和来源筛选 |
| 知识库被 AI 猜测污染 | 无来源规则被反复引用 | 强制证据类型、状态、人工确认和冲突日志 |
| 爆款归因错误 | 只研究高播放、无对照 | 加入普通/低表现案例，保留替代解释 |
| 版权与个人信息风险 | 大量复制视频、收集个人信息 | 最小化、去标识化、保存链接与授权摘要、遵守条款 |
| 成本/权限失控 | 无上限重试、密钥暴露 | 请求/预算上限、失败停止、密钥扫描、最小权限 |

**停止条件**：发现未经授权的数据访问、密钥泄露、费用失控、无法追溯原始来源、Notion 关键数据覆盖/丢失、人工审批被跳过时，立即暂停相应流程，保留日志并向用户报告。
